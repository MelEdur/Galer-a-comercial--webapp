# PostgreSQL Design

## 1. General Principles

- Follow the project instructions defined in the root `AGENTS.md`.
- Use PostgreSQL as the relational database.
- Use SQLAlchemy 2.0 for ORM and database operations.
- Use Alembic for database schema migrations.
- Prioritize data integrity, simplicity and maintainability.
- Inspect the existing database structure before modifying it.
- Avoid unnecessary abstractions and premature optimization.
- Do not introduce another database or ORM.

## 2. Database Modeling

When designing tables and entities:

- Represent each entity with a clear responsibility.
- Use meaningful and consistent table and column names.
- Choose appropriate PostgreSQL data types.
- Avoid unnecessary duplication of data.
- Normalize data when it improves consistency.
- Avoid excessive normalization that makes the model unnecessarily complex.
- Define nullability explicitly.
- Use appropriate default values.
- Consider entity lifecycle and ownership when defining relationships.

## 3. Primary and Foreign Keys

- Define a primary key for every entity.
- Use foreign keys to enforce relationships between tables.
- Choose identifier types consistently across the project.
- Prefer explicit foreign key constraints.
- Define deletion behavior (`CASCADE`, `RESTRICT`, `SET NULL`) according to the business rules.
- Do not use cascading deletion indiscriminately.

## 4. Relationships

Use SQLAlchemy 2.0 relationship declarations and typed mappings.

Consider the appropriate relationship type:

- One-to-one.
- One-to-many.
- Many-to-many.

Guidelines:

- Define both sides of relationships when appropriate.
- Use `back_populates` for bidirectional relationships.
- Configure cascade behavior deliberately.
- Avoid circular dependencies and unnecessary bidirectional relationships.
- Use association tables for many-to-many relationships.
- Add explicit constraints to association tables when necessary.
- Avoid loading large collections unnecessarily.

## 5. SQLAlchemy 2.0

- Use the declarative mapping style with `DeclarativeBase`.
- Use `Mapped` and `mapped_column` for typed model declarations.
- Prefer SQLAlchemy 2.0 query style using `select()`.
- Use `Session` or `AsyncSession` consistently with the project's database configuration.
- Manage sessions through FastAPI dependencies.
- Keep database operations separate from HTTP concerns.
- Use transactions when multiple database operations must succeed or fail together.
- Avoid N+1 queries.
- Use appropriate loading strategies such as `selectinload` and `joinedload` when needed.
- Do not introduce asynchronous database access unless the project architecture requires it.

## 6. Constraints and Indexes

Use database constraints to enforce important data rules.

Consider:

- `NOT NULL`.
- `UNIQUE`.
- `CHECK`.
- Foreign key constraints.
- Composite constraints where appropriate.

Indexes:

- Add indexes to columns frequently used in filtering, joining or sorting.
- Consider indexes for foreign keys when query patterns justify them.
- Use composite indexes only when supported by actual query patterns.
- Avoid creating indexes without a clear purpose.

## 7. Migrations with Alembic

- Use Alembic for every database schema change.
- Generate migrations after modifying SQLAlchemy models.
- Review autogenerated migrations before accepting them.
- Ensure migrations preserve existing data whenever possible.
- Use reversible migrations when practical.
- Never modify an already-applied migration to represent a new schema change.
- Keep migrations small and focused.
- Do not modify the database schema manually as a substitute for migrations.
- Verify migrations can be applied successfully.

## 8. Data Integrity and Security

- Enforce important business constraints at the database level when appropriate.
- Do not rely exclusively on frontend validation.
- Avoid storing passwords in plaintext.
- Do not expose internal database fields through API responses.
- Ensure queries respect authorization and resource ownership.
- Use parameterized queries and SQLAlchemy expressions.
- Avoid raw SQL unless it provides a clear benefit.

## 9. Query Performance

- Retrieve only the data needed.
- Use pagination for potentially large collections.
- Avoid unnecessary database round trips.
- Watch for N+1 query problems.
- Use eager loading when appropriate.
- Do not optimize prematurely.
- Use query analysis when a real performance problem is identified.

## 10. Testing

- Use Pytest for database-related tests.
- Test important relationships and constraints.
- Test persistence and retrieval operations.
- Test migrations when relevant.
- Use isolated test databases or transactions to prevent tests from affecting development data.
- Include tests for invalid or inconsistent data.
- Do not claim tests passed if they were not executed.

## 11. OpenSpec

When implementing an approved OpenSpec change:

- Review its requirements and acceptance criteria.
- Identify affected entities, relationships and constraints.
- Consider the impact on existing data and queries.
- Update SQLAlchemy models and Alembic migrations consistently.
- Verify the implementation against the approved scope.
- Report any unresolved modeling decisions.

## 12. Collaboration

- Coordinate database changes with the backend agent.
- Communicate changes that affect API contracts to the frontend agent.
- Do not modify frontend code.
- Do not perform Git operations.
- Report schema changes, migrations and relevant technical decisions.
